# Handover

> **Когда разработчик уходит, его знания не должны уходить вместе с ним.**
> Направьте Handover на имя пользователя уходящего инженера — он прочитает всё, что тот когда-либо коммитил, ревьюил и отстаивал, — а затем составит переплетённую **Книгу передачи дел** (Handover Book) со ссылками на доказательства для человека, который придёт на его место.

Одна команда. Работает локально. Когда настроен LLM-провайдер (по умолчанию), собранное содержимое репозитория отправляется ему для синтеза; без API-ключа всё остаётся детерминированным и локальным.

```bash
handover gen <username> --repo owner/name
```

---

## Зачем это нужно

`git blame` говорит вам, *кто* написал строку. Но он не может сказать, *почему* — или какие модули незаметно лишатся своего единственного ревьюера, или какое «странное» архитектурное решение на самом деле несёт на себе всю конструкцию. Вики зависят от того, станут ли люди писать добровольно, а прощальные встречи начинаются после объявления об уходе и заканчиваются раньше, чем знания переданы.

Handover закрывает те неявные потери, которые не закрывает ничто другое:

1. **Панорама кода** — каждый модуль, к которому он прикасался, его состояние и история
2. **Реестр неявных знаний** — модули, где он был *единственным* автором или *единственным* ревьюером
3. **Топ-5 рисков** — «что сломается, когда он уйдёт», с ранжированием и оценками, каждый пункт — с цепочкой доказательств
4. **Археология решений** — «почему мы тогда выбрали именно это», с цитатами из реальных обсуждений в PR и issue
5. **30-дневный путь** — план обучения преемника
6. **Вопросы и черновые ответы** — что спросить до последнего дня, а также собственные записанные ответы уходящего инженера

## Быстрый старт

Самый короткий путь — одна команда, без клонирования (нужен **Node ≥ 22.13** со встроенным SQLite — без нативной компиляции):

```bash
npm install -g handover-book

# из GitHub (нужен токен для разумных лимитов запросов):
export GITHUB_TOKEN=ghp_...
handover gen <username> --repo owner/name --html

# или совсем без токена и без сети — читаем локальные клоны этого человека напрямую:
handover gen <username> --git-dir ~/work/api --git-dir ~/work/web
```

Результат оказывается в `handover-data/`:

- `handover-data/<username>.db` — локальный SQLite-индекс (один файл на человека; повторные запуски инкрементальны и почти мгновенны)
- `handover-data/handover-book-<username>.md` — переплетённая книга (с `--html` — печатная однофайловая HTML-копия; печать из браузера даёт PDF)

Предпочитаете запускать из исходников? `git clone https://github.com/a742987/Handover && cd Handover && npm install && npm run dev -- gen <username> --repo owner/name`.

### Команды

| Команда | Что делает |
|---|---|
| `gen <username> -r owner/name` | собрать → проанализировать → отрендерить полную книгу |
| `gen <username> -d ~/clone/dir` | то же самое, но из **локальных git-клонов** — без токена, без сети, подходит и для GitLab/Gitee |
| `collect <username> -r owner/name [-d dir]` | только индексирует историю (уже попавшие в индекс коммиты, PR, ревью и issue пропускаются) |
| `capture <username>` | сесть рядом с уходящим инженером и записать его собственные ответы; они попадают в главу 6 (`--answers q.json` — для агентов и скриптов) |
| `risk <username> [--json]` | вывести Топ-5 рисков из локального индекса |
| `bus-factor <username>` | взгляд на команду: какие модули пополняет коммитами только один человек; объединяется с CODEOWNERS, если в репозитории он есть |
| `gate <username> --files changed.txt` | проверка в CI: затрагивает ли этот набор изменений модули с единственным владельцем? (`--comment`, `--fail-on-match`, `--repo owner/name` — чтобы ограничить многорепозиторный индекс; см. [`examples/sole-owner-gate-action.yml`](examples/sole-owner-gate-action.yml)) |
| `verify <username>` | проверка существования цитат: каждый ref, процитированный в готовой книге, должен существовать в индексе (код выхода 1 при отсутствующих ссылках — удобно для CI, `--json` для машин) |
| `render <username>` | заново отрендерить книгу из индекса, без доступа к GitHub (главы 4-6 обращаются к LLM-провайдеру только если настроен API-ключ; передайте `-r`, чтобы переопределить репозитории из индекса) |

Частые флаги: `--provider openai|anthropic|ollama`, `--model <model>`, `--since <ISO date>` (моменты времени без часового пояса трактуются как UTC), `--data-dir <dir>`, `--refresh` (заново загружает то, что уже проиндексировано), `--html` (печатная HTML-копия книги), `--redact` (удаляет известные форматы секретов из LLM-дайджеста и книги; также `HANDOVER_REDACT=1`), `--no-llm` (пропускает LLM-синтез, даже если ключ настроен, — только детерминированные главы, ничто не покидает машину; также `HANDOVER_NO_LLM=1`). `gen` и `collect` принимают `--author <identity>` для сопоставления имени/почты уходящего инженера в локальных клонах; `capture --list` выводит записанные ответы; `bus-factor` принимает `--top <n>`, `--window <days>` и `--json` для CI.

### LLM-провайдеры

Главы 1–3 вычисляются детерминированно из индекса — они работают всегда, с API-ключом или без. Главы 4–6 синтезирует LLM; **без ключа они откатываются к детерминированным сводкам**, а не падают с ошибкой.

- **Anthropic** — задайте `ANTHROPIC_API_KEY` (провайдер по умолчанию)
- **OpenAI** — задайте `OPENAI_API_KEY` и запускайте с `--provider openai`
- **Ollama** — полностью локально, без ключа: запустите Ollama и выполняйте команды с `--provider ollama`

Каждая глава, созданная LLM, подчиняется одному жёсткому правилу: **цепочка доказательств или ничего.** Утверждения, которые модель не может подкрепить ссылкой на коммит, PR, ревью или issue, должны быть помечены как *(инференс)* — непроверяемым утверждениям не место в документе о передаче дел. Глава 6 никогда не говорит от лица уходящего инженера: черновые ответы помечены как черновики, требующие подтверждения, и только ответы, записанные через `handover capture`, звучат от первого лица. Запустите `handover verify`, чтобы проверить каждую ссылку в готовой книге.

## Как считается риск (и почему ему можно доверять)

```
risk = sole_contribution_ratio
     × change_frequency            (last 90 days, normalized)
     × incident_weight             (commits referencing bug-labelled issues)
     × irreplaceability            (sole reviewer +0.5, sole author +0.25)
```

Каждый пункт Топ-5 рисков перечисляет конкретные коммиты, ревью и issue, обосновывающие его оценку, — каждый со глубокой ссылкой в репозиторий. Формула живёт в [`src/risk/engine.ts`](src/risk/engine.ts) — прочитайте её, оспорьте, настройте под себя.

## Архитектура

```
│  GitHub API  │   │  LLM synthesis│   │  sole-contrib│   │  Markdown +   │
│  (Octokit)   │   │  topic clusters│  │  change freq │   │  print-ready  │

          └────────── SQLite index (one file per person, cacheable) ─────────┘
```

## Плагины для редакторов

Тот же CLI обслуживает три интеграции. Общий слой — **встроенный MCP-сервер** (`handover-mcp`, входит в npm-пакет), который предоставляет `handover_generate`, `handover_collect`, `handover_risk`, `handover_capture`, `handover_search` (поиск по доказательствам только для чтения — для уточняющих вопросов) и `handover_render` как инструменты — любой MCP-клиент может пользоваться ими, не вызывая CLI через оболочку.

```bash
npm install -g handover-book   # puts both `handover` and `handover-mcp` on PATH
```

**Claude Code** — установите комплектный плагин:

```
/plugin marketplace add a742987/Handover
/plugin install handover@handover
```

Плагин автоматически регистрирует MCP-сервер `handover` (через поле `mcpServers` в [`plugin/.claude-plugin/plugin.json`](plugin/.claude-plugin/plugin.json)) и добавляет:

- `/handover:gen <username> --repo owner/name` — полный конвейер, затем сводка Топ-5 рисков
- `/handover:risk <username>` — Топ-5 рисков из уже существующего индекса
- skill, которая обучает агента тому, когда и как запускать конвейер ([`plugin/skills/handover/SKILL.md`](plugin/skills/handover/SKILL.md))

**Codex** — две строки:

1. Зарегистрируйте MCP-сервер в `~/.codex/config.toml`:
   ```toml
   [mcp_servers.handover]
   command = "handover-mcp"
   ```
2. Скопируйте [`codex/handover.md`](codex/handover.md) в `~/.codex/prompts/handover.md`, затем запустите `/handover <username> --repo owner/name`.

**Любой другой MCP-клиент** (Cursor, ZCode, …) — зарегистрируйте `handover-mcp` как stdio-сервер; те же шесть инструментов везде.

## Конфиденциальность и этика — прочитайте это, прежде чем запускать для кого-то

- **Подарок, а не аудит.** Handover существует, чтобы передать преемнику карту, а никогда — чтобы оценивать уходящего. Запускайте его *вместе* с уходящим инженером, а не за его спиной. Его комментарии в ревью и сообщения коммитов будут процитированы перед коллегами — если он не написал бы этого в прощальном документе, этому не место в книге.
- **Локальность прежде всего.** Сбор, индексация и рендеринг выполняются на вашей машине. Единственные сетевые обращения — к API GitHub и к настроенному вами LLM-провайдеру. Выберите **Ollama** — и ни один байт содержимого репозитория не попадёт к третьим лицам.
- **Индекс — чувствительные данные.** `handover-data/*.db` содержит полную историю коммитов вашей команды. По умолчанию он добавлен в gitignore; обращайтесь с этим файлом как с учётными данными.
- **Галлюцинация — это баг, а не особенность.** Вывод LLM должен ссылаться на доказательства; неподкреплённые утверждения должны быть помечены как *(инференс)*. Черновые вопросы-ответы в главе 6 помечены как требующие подтверждения — от лица человека говорят только записанные через `handover capture` ответы. Прежде чем передавать книгу другим, запустите `handover verify`. Не доверяйте ни одной главе, которую вы не сверили с её цепочкой доказательств.
- **Анонимизация** (реальные имена → ролевые коды, для HR-контекстов) значится в роадмапе до выхода любых командных/корпоративных тарифов.

## Разработка

```bash
npm run typecheck   # tsc --noEmit
npm test            # vitest
npm run build       # dist/
npm run dev -- ...  # run the CLI from source
```

Стек: TypeScript · Node (встроенный `node:sqlite`) · Octokit · сменные LLM-провайдеры. CI запускает typecheck + тесты + сборку при каждом push.
